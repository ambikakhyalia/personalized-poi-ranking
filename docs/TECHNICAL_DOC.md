# Technical Documentation — Personalized POI Intelligence & Ranking System

## 1. Problem Formulation

Given a traveler's trip context (destination, dates, interests, budget, mobility,
explicit preferences) and their historical interactions, produce a ranked, weighted
list of Points of Interest (POIs) suitable for a downstream itinerary-planning system.

The system is explicitly **not** an itinerary planner: it stops at "for this traveler
and this trip, these are the POIs that matter most, in this order, with these relative
weights." Two core distinctions drive the design:

- **Preference relevance** (would this traveler want this POI?) vs. **contextual/practical
  compatibility** (does it make sense for this trip — budget, mobility, availability?).
- **Explicit** traveler signals (stated interests/budget/preferences) vs. **implicit**
  signals (inferred from past interactions) — kept as separate feature groups rather
  than hand-blended, so the model can learn how to weigh them.

## 2. Architecture

```
POI Catalog + Traveler/Trip Context + Historical Interactions
        ↓
POI & Traveler Representation (Feature Engineering)
        ↓
Candidate Generation (interest + geo + behavioral history + popularity + long-tail)
        ↓
Personalized Ranking — LightGBM LambdaMART (Learning-to-Rank)
        ↓
Context & Utility Scoring (budget + mobility + availability + geo relevance)
        ↓
Final Weighted POI Recommendations (score + preference relevance + context + confidence)
        ↓
Top-K POIs → Downstream Itinerary Planner
```
Explainability and Evaluation attach to the final output rather than sitting in the
main chain — they consume the ranked/scored result, they don't influence it.

Code layout: `poi_ranker/{data,features,candidates,ranking,scoring,explainability,
evaluation}`, orchestrated by `poi_ranker/pipeline.py`. Entry points live in `scripts/`.

## 3. Data Assumptions

The dataset is synthetic (no real user data available), generated by
`poi_ranker/data/generate.py` with a fixed seed (`poi_ranker/utils/seed.py`) for
reproducibility:

- **~195 POIs** across 3 destinations (Lisbon, Kyoto, Austin), 10 categories,
  power-law-distributed popularity (most POIs are long-tail, a few are "famous").
- **25 traveler/trip profiles** with randomized interests, budget, party type,
  mobility, and an explicit preference flag.
- **~1,700 interactions** sampled *proportional to a synthetic affinity score*
  (interest overlap, budget fit, touristy-preference alignment, mobility fit) rather
  than uniformly or by pure popularity — this is what gives the interaction log an
  actual personalization signal for the ranker to learn from.

Interaction taxonomy → learning signal (`INTERACTION_WEIGHTS` in `taxonomy.py`):

| Interaction | Signal | Interaction | Signal |
|---|---|---|---|
| view | 0.1 | navigate | 0.5 |
| click | 0.2 | visit | 0.8 |
| save | 0.4 | booking | 1.0 |
| share | 0.4 | dismiss | -0.5 (explicit negative) |

Per (traveler, POI) pair, interactions are summed and bucketed into a **graded
relevance label 0–4** (`ranking/labels.py`) used to train the LambdaMART ranker.

## 4. Feature Engineering

**POI content features** (`features/poi_features.py`): category one-hot, normalized
price/rating/duration, log-normalized review count and popularity, and a **novelty
score = 1 − normalized log-popularity** — this is the key feature that lets the model
learn to value local/long-tail POIs independently of raw popularity.

**Traveler representation** (`features/traveler_features.py`) — `TravelerProfile`
dataclass with explicit fields (interests, budget, mobility, party type, explicit
preference) and implicit fields derived from history (tag/category affinity, average
price level and touristy-ness of past positively-engaged POIs, a union of visited-POI
tags, interaction count). `profile.is_cold_start` is `True` when interaction count is 0.

**Cross features** (`features/cross_features.py`) combine both sides: interest-tag
Jaccard overlap, implicit tag/category affinity scores, a touristy-preference-fit that
blends explicit preference with implicit touristy affinity, similarity to previously
visited POIs, and the four context-compatibility scores (imported, not recomputed,
from `scoring/context_scoring.py` — the single source of truth for those functions,
reused by both the ranker's features and the final scoring stage).

## 5. Model Selection

**LightGBM LambdaMART** (`lgb.LGBMRanker`, `objective="lambdarank"`) was chosen over
neural/two-tower models (would need far more data to justify) and pure collaborative
filtering (struggles with cold start and doesn't use content features). It natively
handles mixed numeric/categorical/behavioral features, is fast to train on a small
dataset, and its learned splits are inspectable — consistent with the assignment's
"simpler model, thoughtful features, strong evaluation" guidance over unnecessary
complexity.

## 6. Training Methodology

`ranking/dataset_builder.py` builds one **query group per traveler** (LambdaMART ranks
within a group, i.e., within one traveler's candidate set). Candidates are generated
with the *same* `generate_candidates` function used at inference time, so training and
serving distributions match.

**Cold-start augmentation**: initial experiments showed the ranker generalized poorly
to genuinely new travelers, because every training query group had non-zero implicit
features (all 25 travelers had real history) — an all-zero implicit-feature input at
inference time was out-of-distribution for the model. Fixed by adding a **second query
group per traveler**, built from an *empty* interaction history (same ground-truth
labels, zeroed implicit features), teaching the model to fall back on explicit +
content signals when implicit history is absent. This is what makes new-traveler
cold start actually work end-to-end, not just in candidate generation.

Interactions are split **per-traveler by timestamp** (`ranking/split.py`, 80/20) before
any of this — the last 20% of each traveler's interactions are held out as evaluation
ground truth and never used to build profiles, labels, or training features.

## 7. Ranking Methodology

At inference (`pipeline.py::recommend_for_traveler`):
1. Build the traveler's profile from whatever interaction history is available.
2. Generate candidates for their destination.
3. Score candidates with the trained ranker → raw scores.
4. Min-max calibrate raw scores to 0–1 **within that traveler's candidate set**
   (`scoring/utility.calibrate_preference_scores`) → `preference_weight`.

## 8. Scoring Methodology

Final utility combines three terms with fixed, documented weights
(`scoring/utility.py`):

```
final_score = 0.50 · preference_score + 0.35 · context_compatibility + 0.15 · geo_relevance
```

`context_compatibility` is the mean of budget/mobility/availability compatibility
(`scoring/context_scoring.py`); `geo_relevance` is a distance-decay function from the
destination centroid. Weights were chosen so preference still dominates (this is a
*personalization* system first) while a POI that is impractical (wrong budget, needs a
car when the traveler has none, closed during the trip) is meaningfully demoted rather
than zeroed out — a partially-relevant-but-imperfect POI can still surface.

`confidence` is a heuristic blend of traveler data completeness (more interactions →
higher confidence) and POI data completeness (more reviews → higher confidence),
capturing "how sure are we" independent of the score itself.

## 9. Evaluation

`poi_ranker/evaluation/evaluate.py` computes, on the held-out 20% test interactions:

- **Precision@K, Recall@K, NDCG@K** (K=5,10) — required metrics, against "positive"
  held-out interactions (visit/booking/save/share).
- **Personalization** — `1 − average pairwise Jaccard overlap` of top-K lists across
  all travelers. Near 0 would mean everyone gets the same list; our runs show ~0.95+,
  confirming meaningfully different recommendations per traveler.
- **Long-tail discovery** — fraction of recommended POIs below their destination's
  median popularity. Confirms the long-tail guarantee in candidate generation is
  actually surfacing in final recommendations (~40-45% in our runs).

A "successful result" here is not a high absolute Precision@K (with ~40-90 sparse
interactions per traveler and only 20% held out, recall/precision ceilings are low by
construction) — it is **personalization clearly above 0** and **long-tail discovery
clearly above 0**, proving the system does not degenerate into one universal
popularity ranking, combined with NDCG@10 meaningfully above 0 (ranking is better than
random).

## 10. Cold-Start Strategy

- **New traveler**: implemented. Falls back to explicit-preference + content-based
  scoring; implicit features default to zero/None (`TravelerProfile.is_cold_start`).
  The ranker was explicitly trained to handle this regime (see §6). `confidence` is
  lowered via the traveler-data-completeness term.
- **New POI**: implemented lightly. No popularity/review history contributes via
  `novelty_score` (naturally high for POIs with few reviews) and low `confidence` via
  the POI-data-completeness term; candidate generation's long-tail guarantee also
  helps new/unpopular POIs surface rather than being filtered purely by low popularity.
- **New destination**: documented only, not implemented (allowed by the assignment).
  Approach: none of the model's features are destination-specific IDs — every feature
  (category, tags, price, budget/mobility compatibility, novelty) is destination-
  agnostic, so the trained ranker would transfer directly to a new destination the
  moment its POIs are added to the catalog with the same schema. Confidence would be
  further lowered for a genuinely new destination given the absence of any
  destination-level calibration data.

## 11. Production Considerations

- **Scale**: candidate generation already reduces a destination's full catalog before
  ranking; for a very large catalog, the geo/interest filter would move to an
  approximate-nearest-neighbor or search-index pre-filter (e.g., a spatial index plus
  an inverted tag index) rather than a full in-memory scan per request.
- **Feature computation**: POI content features (category, price, rating, novelty) are
  static and computable **offline/batch**. Traveler implicit features depend on live
  interaction history and would be computed **online** at request time (or
  incrementally updated in a feature store as new interactions arrive).
- **Model serving**: the trained LightGBM model is small and fast enough for
  synchronous request-time scoring of a few dozen candidates; no batch pre-scoring
  needed at this scale.
- **Data freshness**: POI metadata (hours, availability, popularity) should be
  refreshed on a scheduled batch job; user behavior features should update
  incrementally as new interactions stream in.
- **Retraining**: periodic batch retraining (e.g., weekly) as new interaction data
  accumulates, with the cold-start-augmentation step always included so new-traveler
  performance doesn't regress.
- **Feedback loop**: new interactions (views, saves, bookings, dismissals) flow back
  into the interaction log and are included in the next training cycle's labels.
- **Monitoring**: track live Precision/Recall/NDCG against actual subsequent bookings,
  personalization and long-tail-discovery drift over time, candidate-generation pool
  sizes (to catch over-filtering), and confidence-score calibration against realized
  engagement.

## 12. Local Configuration and Reproduction

The prototype runs locally and requires no API keys, credentials, database, or
external service. There is currently **no `.env` file**, and the application does not
read environment variables. `.env` is ignored by Git for future local-only settings;
there are no current variables a user needs to populate. `python-dotenv` is not a
project dependency.

To reproduce the results from a fresh clone, use Python 3.9 or newer, create a
virtual environment, and install the dependencies from `requirements.txt`:

```bash
python3 -m venv .venv
./.venv/bin/python -m pip install --upgrade pip
./.venv/bin/python -m pip install -r requirements.txt
./.venv/bin/python -m pytest tests/ -v
./.venv/bin/python scripts/generate_dataset.py
./.venv/bin/python scripts/run_pipeline.py
./.venv/bin/python scripts/run_scenarios.py
```

Run the commands from the repository root. The fixed random seed makes synthetic
data generation reproducible. The pipeline creates the trained model and evaluation
report locally; the scenario command uses that model to produce the three JSON
recommendation results. On macOS, LightGBM may require `libomp`; installation options
are documented in the repository README. This project does not promise bit-for-bit
identical model metrics across all LightGBM/platform versions, so record the Python,
dependency, and platform versions when reporting results.
